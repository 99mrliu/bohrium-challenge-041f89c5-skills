# protocol-first-evidence-review：协议先行·筛选留痕·证据定位

## 核心主张

选题评估最常见的失真发生在**证据进入之前规则还没定**：先看到几篇顺眼的文献，再回头补一个"看起来系统"的综述。本流水线把顺序强制倒过来：**问题结构化 → 协议冻结 → 筛选留痕 → 证据矩阵 → 综合与边界**。每一步产出可独立复核的物证文件；结论只能引用已进入证据矩阵的材料，协议之后补充的文献必须走"增补登记"而不是悄悄混入。

## 运行时契约（必须先读）

1. 输入在 `/input`：`task.md`（任务说明）、`case.json`（含 `case_id`、`output_contract`，可能还有文献清单、提案文本、约束场景）、以及材料文件（PDF/CSV/JSON 等）。**逐文件读真实内容**，不要依据文件名或标签猜测内容。
2. 先 `cat /input/environment/resources.yaml`（若存在）确认可用工具与资源；PDF 用实际可用的解析工具（pdftotext 或等价物）从原始 PDF 提取，不假设有预提取文本。
3. 一切中间产物写入 `/app/work`，最终交付写入 `/app/output`。`result.json` 必须包含 `case_id` 与 `output_contract` 声明的**全部原始字段**，字段名逐字照抄契约，不增删改名。
4. 预算约束：全程约 64 次模型请求、900 秒、单次响应 16384 token。**第一阶段就写出 result.json 骨架**（契约字段先置 null、`status:"in_progress"`），此后每完成一个阶段就回填一次——任何时候中断都有合法半成品。
5. 禁止伪造：文献不存在就写不存在，检索为空就如实报空，材料读不了就标记 unreadable 并说明原因。`status` 只能是 `success` / `partial` / `failed`，与事实相符。

## 六个阶段（严格按序，每阶段结束回填一次 result.json）

### 阶段 0：取证与契约骨架（≤3 次模型调用）

1. `ls -laR /input`，全部文件登记到 `/app/work/inventory.md`：文件名、字节数、`sha256`、格式、可解析性初判。
2. 读 `case.json`：摘出 `case_id`、`output_contract` 逐字段清单、任务给的固定研究问题/提案/约束。读 `task.md` 逐句标出要求的交付物。
3. 写 `/app/output/result.json` 骨架（字段=契约字段，值=null，`status:"in_progress"`，附 `provenance`：输入文件哈希清单、工具版本）。

### 阶段 1：研究问题结构化

按 `templates/question_frame.md` 把任务给的研究问题（或提案设想）拆成可检验要素并写入 `/app/work/question_frame.md`：

- 研究对象、关键变量（自变量/因变量/混杂变量）、比较基线、预期结论方向、**可证伪条件**（什么观察结果会推翻该设想）；
- 若任务文本缺少某要素，标 `未指定` 并说明该缺失对后续筛选的影响，**不替任务脑补**；
- 输出一句话可检验问题陈述，格式："在【对象/场景】下，【干预/方法】相比【基线】是否/多大程度影响【结局指标】，可通过【观察/测量】检验。"

### 阶段 2：协议冻结（先定规则，后看文献）

按 `templates/protocol_template.md` 写 `/app/work/protocol.md`，**在打开任何一篇文献全文之前完成**：

- 证据来源清单：本题以 `/input` 提供的文献集为第一来源；若运行环境确有联网检索工具且在 task.md 允许范围内，列明检索式（完整布尔串，含字段限定）、时间窗、语言范围；**没有可用检索通道时，明确写"检索范围 = 输入文献集"，并声明这是覆盖边界而非"该领域尚无人研究"**；
- 纳入标准与排除标准：每条写成可对一个文献记录机械执行的判定句（含阈值、时间窗、研究类型），并给一条排除示例；
- 证据字段表头：定义证据矩阵要抽的列（见阶段 4），先定列再读文献。

### 阶段 3：筛选留痕

按 `templates/screening_log_template.md` 对每一条候选文献记录在 `/app/work/screening_log.md` 逐行判定：`纳入 / 排除 / 待定`，排除必须引用协议中具体标准编号并写一句理由；`待定` 条目说明缺什么信息、最终如何处置。筛选完成时统计：候选 N、纳入 n、排除明细。若纳入数为 0 或 1，**不要扩大标准硬凑**，转入异常处理（见下）。

### 阶段 4：证据矩阵

按 `templates/evidence_matrix_template.md` 建 `/app/work/evidence_matrix.md`，对每篇纳入文献逐行抽取：任务/研究对象、方法、数据/材料、评价方式、主要结论、与本研究问题的关系、**来源定位**（文件名+页码或小节名，PDF 给出页码；JSON/CSV 给出记录 ID 或行号）。两条规定：

- 每个单元格的内容必须能在该文献的定位处找到原文依据；抽不到就写 `未报告`，禁止用领域常识补；
- 结论相反的文献**必须入矩阵**并在"关系"列标 `冲突`，不得只留支持性证据。

### 阶段 5：综合、创新边界与可行性

在 `/app/work/synthesis.md` 完成四项交付，全部引用证据矩阵的行号：

1. **已有工作比较**：按矩阵归纳谁做到了哪一步，指出真正相近的工作与无法直接比较的工作（写明不可比原因：任务不同/指标不同/数据不公开等）；
2. **创新点识别**：对任务提案的每条创新陈述，判定`已被覆盖 / 部分覆盖 / 未见覆盖 / 无法判定`，每条给出所依据的矩阵行；"未见覆盖"必须同时写明检索范围边界（本判断限于协议声明的来源与时间窗）；
3. **可行性判断**：核查数据可得性、实验/计算条件、时间窗、方法成熟度四类前提，每条前提标 `[来源:矩阵行号]` 或 `[假设]`；输出带条件的结论（可行 / 有条件可行+条件清单 / 不可行+障碍 / 证据不足）；
4. **研究空白与不确定性**：列出空白点、冲突证据的取舍理由、无法确定项。

### 阶段 6：收口

1. 把结论按契约逐字段回填 `result.json`；证据矩阵、筛选日志、协议文件按契约要求复制或引用到 `/app/output`；
2. 逐条过 `checklists/final_checklist.md`，全部通过才允许 `status:"success"`；任一不达标则 `partial` 并在不确定性字段写明缺什么、为什么；
3. 在 result.json 的变更/状态记录字段（如契约提供）写明各阶段完成时间与中途修订。

## 异常处理手册（对号入座，不许静默跳过）

| 情形 | 处置 |
|-|-|
| 文献集为空或全部排除 | `status:"partial"`；交付问题结构化、协议、空筛选日志与"无法形成综合结论"的明确说明；给出若补充文献后协议如何复跑 |
| 只有 1–2 篇可纳入 | 正常出矩阵，但综合结论降级为"初步证据"，每条结论注明单源风险 |
| 证据互相冲突 | 双方均入矩阵；综合段写明冲突点、可能原因（方法/样本/指标差异）、本评估的取舍及理由 |
| PDF 无法解析/乱码 | 换工具重试一次；仍失败则该文献标 `unreadable` 排除并登记，不用摘要冒充全文 |
| 检索接口异常/无权限 | 记录请求与错误；检索范围降级为输入文献集并在协议中修订登记（协议可因通道失败修订，但修订本身必须留痕） |
| 时间/预算将尽 | 立即回填当前最好结果到 result.json（`partial`），优先保证契约字段齐全，再补分析深度 |

## 红线

- 不许把"检索不到"写成"尚无人研究"；不许不读全文就抽取结论；不许为凑数放宽纳排标准；不许只登记支持性证据；不许交付没有来源定位的"事实"；不许先写结论后补证据。
