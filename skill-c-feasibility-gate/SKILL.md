# feasibility-gate-decision-memo：前提对账·五道门·带条件结论

## 核心主张

可行性判断最常见的失效形式是一句没有前提的"技术路线可行"。本 Skill 把可行性当成**一组可核查前提的合取**：任何一道门 fail 且无法缓解，整体就是 no-go；前提没有来源就是假设，假设必须显式列出并给出验证方式。**结论的价值不在 go 或 no-go，在于条件清单和风险登记可以被逐条复核。**

## 运行时契约（必须先读）

1. 输入在 `/input`：`task.md`、`case.json`（`case_id`、`output_contract`、提案与约束场景）、材料文件。**逐文件读真实内容**；PDF 用环境实际可用工具从原始 PDF 解析；先 `cat /input/environment/resources.yaml`（若存在）确认工具与资源。
2. 中间产物写 `/app/work`，最终交付写 `/app/output`。`result.json` 含 `case_id` 与 `output_contract` **全部原始字段**（字段名逐字照抄）。
3. 预算约 64 次模型请求、900 秒、单次 16384 token。**第一步写 result.json 骨架**（契约字段置 null、`status:"in_progress"`），每道门判完回填一次。
4. 诚实约束：不伪造设备、数据、经费或文献；前提查不到来源就标 `[假设]`；`status` 只能是 `success`/`partial`/`failed`。

## 七个阶段（严格按序）

### 阶段 0：取证与骨架（≤3 次模型调用）

`ls -laR /input` 登记 `/app/work/inventory.md`（文件名、字节数、sha256、可解析性）；读 `case.json` 摘出 `case_id`、契约字段、提案与**约束场景**（数据规模、设备、周期、团队等一切显式约束）；写 `/app/output/result.json` 骨架。

### 阶段 1：决策问题陈述

把"能不能做成"改写为可检验陈述，写入 `/app/work/decision_frame.md`：研究目标、成功判据（什么指标达到什么阈值算做成）、最低可接受结果、终止条件（什么证据出现时应当放弃）。成功判据只能来自 task.md/case.json/文献，缺什么标 `未指定` 并说明对门判定的影响。

### 阶段 2：前提台账

按 `templates/premise_ledger_template.md` 建 `/app/work/premise_ledger.md`：从提案与约束场景抽出全部前提，逐条编号 Q1…Qn，每条标门类（数据/算力/实验条件/时间窗/人员与方法）与状态：

- `[来源:文件+页码/小节/记录号]`——材料或文献直接支持；
- `[推断:由哪条来源经什么推理得到]`——有依据的间接结论；
- `[假设:验证方式]`——无来源，必须附"如何验证该假设"（查什么、问谁、做什么小实验）。

### 阶段 3：五道门判定

按 `templates/gate_checklist_template.md` 逐门判定，写入 `/app/work/gates.md`：

1. **数据门**：所需数据是否存在、可获取、规模与质量是否够（对照文献中同类工作的数据规模）；
2. **算力门**：模型/计算量级与可用算力是否匹配（以文献报告的资源需求为参照）；
3. **实验条件门**：设备、材料、环境、伦理/合规许可；
4. **时间窗门**：各关键环节耗时估计与截止期限的关系，含排队/返工缓冲；
5. **人员与方法门**：方法成熟度（文献中是否已有可复现实现）、团队技能覆盖、关键依赖方。

每门输出四态：`pass`（全部前提有来源）、`conditional`（有假设但给了验证方式与缓解）、`fail`（有前提被证据否定）、`unknown`（关键前提无来源也无验证路径）。**判定必须引用前提编号。**

### 阶段 4：失败模式登记

按 `templates/risk_register_template.md` 建 `/app/work/risk_register.md`：对每个 conditional/fail/unknown 前提，登记失败模式（会发生什么）、触发信号（如何尽早发现）、影响（对哪道门/哪个判据）、缓解措施、残余风险。缓解措施必须具体（换数据源/降规模/先跑 pilot），不许写"加强管理"式空话。

### 阶段 5：参照系——已有工作与创新边界（压缩版）

可行性判断需要一个参照系：文献中最近的工作用多少数据、多少资源做到了什么。在 `/app/work/baseline_scan.md` 中对每篇对照文献抽取一行：任务、方法、数据规模、报告的资源/条件、结论、定位；并一句话说明提案相对最近工作的差异点（该差异点是否正是风险来源，回链到风险登记编号）。本阶段只做到"够支撑门判定"的深度，不做完整综述。

### 阶段 6：带条件结论与收口

输出结论，四选一，写入 result.json 对应契约字段：

- `go`：五门全 pass，风险登记无未缓解的高风险；
- `conditional-go`：附**条件清单**（每条=一个假设的验证方式+时限）与风险登记；
- `no-go`：附不可逾越障碍清单（引用证据）与若要翻盘需要什么条件变化；
- `indeterminate`：附关键缺口清单与补足路径。

同时回填：问题定义（阶段 1）、比较与创新边界（阶段 5）、不确定性（假设清单、冲突证据、空白）。过 `checklists/gate_final_checklist.md`，任一不过则 `partial`。

## 异常处理

- 约束场景缺失（未给数据/算力/周期信息）：相应门直接判 `unknown`，前提记 `[假设:验证方式]`，不得虚构约束；
- 文献未报告资源需求：用同方法族文献的数量级作 `[推断]` 并写明推理链；
- 证据冲突（如两篇文献报告的资源需求差数量级）：双方都登记，门判定取保守一侧并说明；
- 材料不可读/接口异常/权限不足：登记事实与受影响的门；
- 预算将尽：立即回填当前门判定与台账（`partial`），优先保证结论字段与条件清单完整。

## 红线

- 不许给没有前提编号的"可行"；不许把假设写成事实；不许用"技术路线可行"概括五道门；不许略过 fail 前提直接给 conditional-go；缓解措施不许是空话；不许虚构约束或资源。
