# claim-centric-novelty-audit：主张拆解·最近邻对账·逐条划界

## 核心主张

创新性评估的失真很少来自文献读得少，更多来自**主张没有被当成可判定的对象**：一句"本文提出了新方法"既无法证实也无法证伪。本审计把提案拆成编号原子主张，每条主张配一本对账账：它属于哪类创新、最近的已有工作是谁、差异点具体到哪一行、反证是什么。**结论的粒度等于主张的粒度**——不做"整体上有创新性"这种无法复核的笼统判定。

## 运行时契约（必须先读）

1. 输入在 `/input`：`task.md`、`case.json`（`case_id`、`output_contract`、可能的提案文本与约束）、材料文件。**逐文件读真实内容**；PDF 用环境实际可用工具从原始 PDF 解析，不假设有预提取文本；先 `cat /input/environment/resources.yaml`（若存在）确认工具清单。
2. 中间产物写 `/app/work`，最终交付写 `/app/output`。`result.json` 含 `case_id` 与 `output_contract` **全部原始字段**（字段名逐字照抄）。
3. 预算约 64 次模型请求、900 秒、单次 16384 token。**第一步就写 result.json 骨架**（契约字段置 null、`status:"in_progress"`），每阶段结束回填一次。
4. 诚实约束：文献必须真实存在于输入材料或已登记的检索结果中；判不下去就写 `undeterminable` 并说明缺什么；`status` 只能是 `success`/`partial`/`failed`。

## 七个阶段（严格按序）

### 阶段 0：取证与骨架（≤3 次模型调用）

`ls -laR /input` 登记 `/app/work/inventory.md`（文件名、字节数、sha256、可解析性）；读 `case.json` 摘出 `case_id`、契约字段清单、提案文本；写 `/app/output/result.json` 骨架。

### 阶段 1：主张分解

从提案/task.md 中抽取全部创新陈述，拆成**原子主张**（一条主张只断言一件事），写入 `/app/work/claim_ledger.md`（模板 `templates/claim_ledger_template.md`）：

- 编号 C1…Cn；每条主张记：原文摘录（含在 task.md/case.json 中的位置）、改写后的可判定陈述、**类别**（方法创新 / 数据创新 / 场景迁移 / 结论修正 / 工程组合）；
- 改写规则：把"全新""首次""大幅"等修饰语换成可核对的内容（对什么对象、在什么指标上、相对哪个基线）；
- 提案未明示但评估必需的隐含前提（如"所需数据可获得"）单列 P1…Pm，不混入创新主张。

### 阶段 2：最近邻识别（每条主张一本账）

对每条主张，在输入文献集（及环境允许的检索通道，若有）中找 **1–3 篇最近邻工作**：判断相近的维度按 `任务相同 → 对象相同 → 方法族相同 → 指标可比` 依次放宽，放宽到哪一级就记录到哪一级。写入 `templates/nearest_neighbor_template.md` 的对应表。

- 找不到相近工作时：必须记录**已执行的查找动作**（查了哪些记录、用什么词、到哪一级放弃），然后主张状态记 `未见覆盖（边界：已查范围=…）`——**禁止**写"国际/国内尚无人研究"；
- 候选文献不足以判定时标 `undeterminable`，说明缺的是全文、数据还是指标口径。

### 阶段 3：逐条覆盖判定与边界声明

对每条主张给出四态判定并写**边界声明**：

| 判定 | 含义 | 必须附上的内容 |
|-|-|-|
| covered | 已有工作完整覆盖 | 最近邻编号 + 覆盖点定位（文件+页码/小节） |
| partially_covered | 部分覆盖 | 已覆盖部分与**剩余差异点**（具体到对象/指标/条件），差异点的最小可验证实验 |
| not_covered | 在已查范围内未见覆盖 | 已查范围声明 + 差异点 + 该判断可推翻的条件（出现什么文献即推翻） |
| undeterminable | 证据不足 | 缺口清单 + 补足缺口所需的材料 |

边界声明句式固定为："主张 Ci 超出【最近邻 Wj】之处在于【具体差异】，该差异可通过【观察/实验】验证；此判断在【已查范围】内成立。"

### 阶段 4：反证登记与取舍

按 `templates/counter_evidence_template.md` 登记与主张结论相反的文献：冲突点、双方定位、冲突的可能机制（样本/方法/指标差异）、本审计的取舍及理由。**只登记支持性证据视为审计失败**。若未发现反证，必须写明"已在 X 范围主动寻找反证，未见"——主动寻找这个动作要留痕。

### 阶段 5：派生交付——问题定义与可行性对账

- **问题定义**：把主张集合归并成一句话可检验研究问题（对象/变量/基线/预期/证伪条件），写入 claim_ledger 末尾；
- **可行性对账**：把阶段 1 的隐含前提 P1…Pm 逐条核查：数据、算力、实验条件、时间窗、方法成熟度，每条标 `[来源:文献定位]` 或 `[假设]`；输出带条件的可行性结论（可行 / 有条件可行+条件 / 不可行+障碍 / 证据不足）。

### 阶段 6：收口

回填 result.json 各契约字段（主张台账、边界声明、反证登记按契约要求组织）；过 `checklists/audit_checklist.md`；任一项不过则 `partial` 并写明缺口。

## 异常处理

- 提案中没有显性创新陈述：从任务目标反推主张并在台账中标注"由任务目标重构"，不凭空发明；
- 文献过少（<3 篇可对照）：照常出账，但所有 `not_covered` 判定降级措辞为"在仅有的 N 篇对照内未见覆盖"；
- 文献互相冲突：按阶段 4 处理，相关主张不得给确定性判定；
- 材料不可读/接口异常/权限不足：登记事实与影响范围，受影响主张记 `undeterminable`；
- 预算将尽：立即回填当前台账（即使只有部分主张完成判定），`status:"partial"`。

## 红线

- 不许给没有最近邻对账的"新"字背书；不许把场景迁移包装成方法创新（类别标错=审计失败）；不许把"没查到"写成"不存在"；不许只登记支持性证据；不许交付无定位的覆盖判定。
